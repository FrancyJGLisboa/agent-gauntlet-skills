Agent Gauntlet

Agents can write the code. This makes them prove it works.

Ask for what you want in your own words. Independent agents build it, try to tear it down, and repair what breaks — while a deterministic runtime, not the agents, decides what counts as done. You get a verdict, not a claim.

# describe it however roughly, then walk away
gauntlet deliver --request-file gauntlet-request.md --host claude

The problem it solves

A coding agent will tell you it is finished. It will sound confident. It may have run no tests, written a test that cannot fail, or fixed the symptom you described rather than the fault underneath.

If you can read the diff, you catch it. If you cannot — because you are the person who understands the domain rather than the code — you have no way to check, and "done" is just a word.

Agent Gauntlet exists so that the word means something specific.

What "verified" actually guarantees

Not a feeling. Five mechanical properties, enforced by the runtime rather than requested in a prompt:

  • The agent that wrote the code did not approve it. Criticism happens in a separate process that never sees the builder's reasoning — only the result.
  • Tests were executed by the runtime, never claimed by an agent. Output is hashed and stored. An agent cannot report a pass that did not happen.
  • Pass and fail were defined before the work started. Success comes from the compiled contract, not from an agent's judgment at the moment it is being judged.
  • Nothing touched your working tree until it was verified. Every attempt happens in an isolated checkout; only verified commits are merged back.
  • It stopped on its own. Repairs are capped. A run ends verified or blocked — it does not drift, and it does not need you watching.

What you write, and what you get back

You are not asked to write a specification. Deriving the acceptance criteria is the tool's job — asking you for them would defeat the point of having it.

You write

What you want, in your own words. Who it is for. What evidence exists — a repo, a video, an article. What you have access to, and what you do not. What would make it a failure.

It derives

The architecture, the execution plan, and the tests. One sentence asking for a CSV-to-JSON tool produced 26 acceptance tests covering RFC 4180 quoting, CRLF and byte-order marks, ragged records, and a four-value exit-code contract.

The most valuable thing you can write is the last one, and it needs no technical vocabulary. "It must never show me a stale price as if it were current" is enough to derive a freshness check, a test that fabricates a stale feed, and an instruction to a critic to go looking for exactly that failure.

How a run proceeds

1CompileYour request becomes an executable contract: objective, architecture with the evidence behind each decision, execution plan, and acceptance tests. The contract is fingerprinted and frozen.
2BuildEach slice of work gets a builder in its own isolated checkout, allowed to touch only the files that slice declares.
3TestThe runtime runs the declared commands itself and records exit codes, output hashes, and environment.
4CriticiseA fresh critic sees the result and the captured evidence — never the builder's explanation — and tries to find what is wrong.
5RepairFailures return to a builder, up to three attempts. A defect owned by earlier work reopens that work instead of being patched over.
6VerifyA clean checkout containing only committed content is built and tested from scratch, more than once — which catches work that only passes because of something never committed.
7ExplainA Product Passport records what was built, why the architecture was chosen, how to run it, and precisely what the evidence proves.

Judging quality, not only correctness

A test can prove a program behaves. It cannot prove the result is any good. So a contract may name a reference bar — a real artifact the work has to beat — and the runtime stages the two side by side under neutral names.

Three independent judges see two files called A and B and a single question. They are not told which one is the candidate, and the runtime, not the panel, decides which is which and whether the votes reach the declared threshold. A split panel is inconclusive, and inconclusive is never approval.

When it stops instead of finishing

Sometimes the honest answer is that it cannot be done. A stopped run writes a plain-language account of why: what was attempted, what stopped it, what is recommended, what that would cost, and what happens if you do nothing.

If a decision is genuinely yours — a credential, a budget, a legal call — you are asked for exactly that. If what remains is a technical judgment, the runtime deletes the question rather than passing the buck, and tells you plainly that no answer of yours can unblock it. Being asked to adjudicate a library choice you have no basis to evaluate is not help.

Where it fits

Good fitPoor fit
A bounded new capabilityA sweeping refactor
Adapting a reference to new dataA one-line change
Work worth half a day to two daysAnything you could review in ten minutes
Work you want audited laterExploration where you want to steer

The enforcement costs real time — several minutes per slice, and more when a reference bar is being judged. That is worth paying when you cannot personally check the result, and wasteful when you can.

Install

# the skills, so /compile-gauntlet works in any repository
git clone https://github.com/FrancyJGLisboa/agent-gauntlet-skills.git
cd agent-gauntlet-skills && bash scripts/install.sh claude

# the runtime, which is what actually enforces anything
cd packages/gauntlet-cli && npm install && npm link

Needs Node 24 or newer and an authenticated Claude Code, Codex, or GitHub Copilot CLI. The target project must be a Git repository with a clean working tree.

Prompting inside your agent's chat writes the contract. The runtime has to be the thing that executes it — a single conversation cannot be both the builder and the independent critic, which is the guarantee you came for.

Honest status

This is early software, version 0.x, and the interesting parts are the guarantees rather than the polish. Worktree isolation, contract-defined pass conditions, and end-to-end runs from a one-line request have been exercised against live agents. Blind judging and clean-room verification are covered by tests but have not yet been run at scale.

The Codex and Copilot adapters are implemented and untested. Reported limitations in the Product Passport are deliberate: a claim with no evidence behind it does not appear there at all.
